## Review of the day's new code, and what it found

An independent read of the four gesture modules and the finger capture before
the worn session. Five real defects, all fixed:

1. **The tag gesture could not move the tag.** The mod's
   `HudElementSmartTagging._find_raycast_targets` hook *replaces* the stock
   method and returns the cached reticle, which belongs to the weapon hand;
   `tag_role()` only fed a nil check, so pointing changed nothing. Now, while
   the off hand points, the hook hands the whole raycast back to stock, which
   goes through `force_update_smart_tag_targets` and therefore through the
   role. The override remains for the weapon hand, whose reticle is already
   traced and cached. The tester would have reported a threshold problem.
2. **The tag pose was judged from the grip but consumed as an aim.** Those are
   separate tracking channels, so a hand with a usable grip and no usable aim
   handed tagging to a hand with no ray, falling back to stock screen-centre
   targeting: worse than the weapon. It now requires
   `hand_aim_usable("support")`.
3. **Reach took over the interaction target while merely approaching** (0.75 m,
   no grip involved), which changed what the ordinary interact button did, and
   what a tag picked, without the player reaching for anything. The claim still
   exists while approaching, so the grip grace works; the target only moves
   once the hand has arrived.
4. **Reach measured to the unit's root**, which for a downed team mate is their
   feet and for a door its origin, often a metre from the panel the hand is on,
   so the advertised targets could sit in "approach" for ever. It measures to
   the node the stock search hit, which it already had.
5. **The finger capture counted steady frames per hand but not per weapon**, so
   a swap that settled immediately could cache a pose taken one frame in; and
   the pose cache survived a rig respawn that rebuilds the node list it is
   indexed into, which would land rotations on the wrong joints. Both fixed.

Also: all four gestures latched a single `pcall` failure and switched
themselves off for the rest of the session, with `destroy()` never called by
anything, so there was no way back short of restarting. They now count failures
and keep running, as `sight_ads` already did. The reach search runs every other
frame with its targets re-measured against live hand positions in between
(two physics overlaps per input frame was 2-3x the stock interactable work for
an idle feature), and the inspect option now says it is off in the hub, which
it always was.

Confirmed sound and left alone: the forced-action masks and the fact that
nothing can stick a microphone or an inspect on, the nil guards before every
vector subtraction, and both hysteresis pairs.

- Run `gest4` verified the fixes with all four gesture flags on: scene at 73 s,

## Performance: a Lua frame profiler, because nothing measured the mod's own Lua

- The user asked for performance work once the queue was empty, and named the
  Hub as the least performant zone and the real VDXR to Virtual Desktop
  pipeline as the one to measure on (not the simulator, whose overhead is
  lower). Every earlier performance pass in this repo is native or GPU side;
  the mod's own per-frame Lua, to which today added seven samplers on the
  main thread, had never been timed.
- `darktidevr_frame_profile.lua` (test `frame_profile`): opt-in through
  `darktidevr_frame_profile.flag`. Sections are timed with
  `Application.time_since_launch`, the stock high-resolution clock (`os.clock`
  is a millisecond on Windows). Every 5 s it logs `mod_ms_per_frame` and the
  top twelve sections by cost with per-frame, per-call mean and max figures;
  bounded to 40 reports a session, and each report is a fresh window so a
  change shows in the next one. Off, a section is one branch and a tail call.
- Wrapped: every sampler in `inject_gameplay_input` (sights, inspect, comms,
  tag, communication wheel, two-hand, holsters, reach, radial, bindings,
  haptics), the draw pass (gun aim, ammo readout, holster counts, wrist
  display, radial, forearm holsters, teammate status, body mirror) and the
  render-path draws (weapon charge, crosshair feedback). The wrapper returns up
  to four values, which covers every call site, and allocates nothing.
- Four slice tests anchored on the exact draw-call text and needed their
  anchors moved to the wrapped call; one needed a `frame_profile` stub. The
  ordering those tests check is unchanged. 272 pass.
- Checklist item 22 is the "nothing should look different" note.
- Next: a baseline in the Hub with the flag on and every option off (what
  every player pays), then with every option on, then cut the top of the list.
- First Hub run (`hub-defaults1`) with the profiler on: enabled, 18 reports,
  about 281 input frames per 5 s window — and **every section exactly zero**,
  mean and max alike. `Application.time_since_launch` is frame-quantised, so
  two reads inside a frame return the same value; the unit test could not have
  caught that. The native module already exports `dtvr_qpc_ticks` and
  `dtvr_qpc_frequency` (the render-timing diagnostic uses them), so the
  profiler now takes that clock from its installer. No native rebuild, no
  kernel32 cdef. The enabled line reports `clock=qpc hz=...`, which is how the
  next run proves the clock ticks.
