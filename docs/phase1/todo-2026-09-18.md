## From the FOV-tangent audit (Opus, 17 September; none of these is done)

The user runs Virtual Desktop's FOV tangent at 90 per cent and expects many
players to. It shrinks the eye target (2112x2304 to 1908x2076) and Virtual
Desktop then draws OpenXR quad layers with a mismatched projection. Done so
far: boards and menu pointer into a projection layer, overlay cells and text
fitted, an atlas gutter.

- [ ] **Gameplay reticle out of Virtual Desktop's quad layers.** Still
  `gameplay_reticle_quad` in `local_space_` (`src/xr/main.cpp`, near the
  `ads_vignette_quad`). Estimated error from the same fault that moved the
  boards: none dead ahead, about 1 degree at 10 degrees off the view's
  centre, 2.5 at 30 (17 to 44 cm at 10 m), swimming as the head turns
  against the aim. The `PanelRenderer` path already has what it needs: the
  reticle sprite lives in the flat capture texture, which is the renderer's
  board texture, so it is a third `Source::board` quad with the pose, size
  and texels already computed for the quad. Two changes: submit the board
  projection layer in gameplay for the reticle alone (cleared transparent;
  today it is only submitted when a board shows, and the board texture copy
  only happens on `use_flat_capture`, so the atlas-sprite copy path must
  also write `panel_renderer->board_texture()`), and keep
  `maximum_quads_per_eye = 4` in mind (the three pointer quads are menu
  only). Cost to measure: a second projection layer every gameplay frame
  through Virtual Desktop's compositor; take a Hub frame-profile arm before
  and after, and keep the quad behind `DTVR_XR_BOARD_PROJECTION=0`.
  Measure the real error first if possible (a reticle held on a fixed world
  point while the head turns 30 degrees).
- [ ] **ADS vignette sized from the field of view**, not a fixed 3.6 m at
  1 m (`src/xr/main.cpp`, `ads_vignette_quad.size`): at 90 per cent the
  darkening starts about 10 per cent further into view. Head-locked, so the
  quad fault itself only changes its radius; scale by the runtime's corner
  tangent. Cosmetic.
- [ ] **World marker size may depend on the desktop window's height.**
  `marker_head_frame` (`darktidevr.lua`, about line 15815) divides the
  rendered FOV by `Application.back_buffer_size()` height while marker
  pixels are authored at `RESOLUTION_LOOKUP` (the eye target). If the back
  buffer is the desktop client, markers change about 10 per cent in world
  size with the tangent and with the player's window size. One `mod:info` of
  both heights at level start settles it (put it in the proving run); the
  fix is `RESOLUTION_LOOKUP.height`.
- [ ] **Also unconfirmed**: whether `RESOLUTION_LOOKUP.scale` is exactly
  `width / 1920` at 1908 (0.99375) or quantised; a quantised value would put
  the published menu `source_width/height` a few pixels off the viewer's
  flat swapchain. Log it in the same run.
- [ ] **Tooling that assumes 2112x2304** (does not affect play):
  `tests/xr_harness/shared_eye_capture.cpp` and
  `tests/shared_eye_surfaces/main.cpp` default the extent and then time out
  with "Timed out waiting for producer-owned shared eye surfaces" (take it
  from `openxr.recommended_size`, as
  `tools/stereo/resolve-synthetic-eye-size.ps1` does);
  `tools/stereo/analyze-shared-eye-edge-stability.py` and
  `analyze-shared-eye-cull-ab.py` default 264x288 and the full-FOV

  `src/xr/main.cpp` and `darktidevr.lua`;
  `tools/stereo/test-darktide-lua-invariants.ps1` pins `2112.0F / 2304.0F`.
