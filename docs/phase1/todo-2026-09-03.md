## 6. DLSS Frame Generation for XR

Current finding: Darktide's existing Streamline DLSS Frame Generation is
attached to the desktop DXGI swapchain and runs at `Present`. The XR bridge
captures and submits the two eye resources before that boundary, so Steam can
report generated desktop frames while the headset still receives only fresh
rendered stereo pairs. Do not treat the mirror counter as headset delivery.
The inspected installation currently carries Streamline `2.7.30.0` and
`nvngx_dlssg.dll` `310.2.1.0`; runtime instrumentation must report rather than
hard-code those versions because game updates can replace them.

Research basis:

- NVIDIA's [DLSS Frame Generation programming
  guide](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS_G.md)
  makes the backbuffer an automatically intercepted `Present` resource. It
  allows independently tagged viewports, but they all write to one backbuffer,
  and it does not support multiple swapchains.
- The same guide requires depth, motion vectors, frame-matched common constants
  and long-lived resources through `Present`; hudless colour and UI colour/alpha
  are strongly recommended. Reflex is required.
- OpenXR's [`XR_EXT_frame_synthesis`](https://registry.khronos.org/OpenXR/specs/1.1/man/html/XR_EXT_frame_synthesis.html)
  is a separate, runtime-owned alternative using per-view depth and motion
  vectors. It is not DLSS and must be capability-probed on VirtualDesktopXR.

Implementation path, in proof order:

1. **Instrument without changing presentation.** Record the loaded Streamline
   version and feature requirements; the game and proxy swapchain identities;
   `Present` call/thread/frame identity; `slDLSSGGetState` support, maximum
   generation count and `numFramesActuallyPresented`; and correlation with
   left/right ready fences. Establish whether generated asynchronous presents
   traverse the proxy and whether a generated backbuffer is accessible.

   The observe-only layer is complete. `start-darktide-vr.ps1
   -StreamlineProbe` creates a launch-scoped flag and writes bounded samples to
   `%TEMP%\darktidevr-streamline-probe.tsv`. It adds no Streamline API calls:
   it wraps Darktide's existing `slDLSSGGetState` and `slDLSSGSetOptions`
   functions and forwards each invocation exactly once before recording it.
   A live run proved that the hooked `Present` implementation is owned by the
   loaded `sl.interposer.dll` 2.7.30.0 and that `sl.common.dll` and
   `sl.dlss_g.dll` 2.7.30.0 plus `nvngx_dlssg.dll` 310.2.1.0 are resident.
   Fifty-six samples retained one Present thread, swapchain and COM identity;
   after stereo attached, the same samples tracked DarktideVR's ready fence at
   either the current value or one completion behind. The configured game
   settings requested DLSS-G with one generated frame.

   A second 90-second run captured Darktide's own calls. Its capability query
   succeeded with state ABI version 3, status 0, minimum dimension 100, maximum
   generation count 1 and an input-completion fence. During startup it supplied
   mode 0 on viewport 1488243306; from sampled option call 2,760 / Present 4,574
   onward it supplied mode 1 on viewport 1821058217 with one frame requested.
   All sampled setters returned success. The run submitted 8,461/8,461 OpenXR
   frames and delivered 1,402 fresh pairs with zero reuse, capture failures,
   stale frames, pair-driven timeouts or pose mismatches. This proves that live
   DLSS-G was requested on the gameplay viewport without the observer changing
   the game's call count.

   The next lower-boundary probe is also complete. Streamline's documented
   private base-interface query exposed the native swapchain and its Windows
   `dxgi.dll` Present target. Before mode 1, native and outer presents remained
   1:1. After activation, native calls appeared on a second thread against the
   same swapchain. At sampled outer frame 6,120 the native count was 7,653, a
   surplus of 1,533 calls: effectively one generated present for each rendered
   frame since activation. The asynchronous hook could obtain the current
   backbuffer before the native Present; sampled generated calls exposed a
   2496x2688 `DXGI_FORMAT_R8G8B8A8_UNORM` resource. This proves that generated
   presentations traverse a pre-scanout seam where their swapchain resource is
   addressable. It does not yet establish safe GPU synchronization, exact
   source/generated pair indexing, or a non-blocking copy into XR-owned
   surfaces.

   Do not add an independent `slDLSSGGetState` call: the exact 2.7.30 header
   marks it non-thread-safe and defines `numFramesActuallyPresented` since the
   previous call, so an extra observer can change the application's result.
2. **Find the exact per-eye inputs.** Identify final/hudless colour, depth,
   motion vectors, UI/alpha, common constants and Streamline frame token for
   each eye. Calibrate vector units, sign, Y direction, jitter removal and
   current/previous history independently for both eyes. Retain every tagged
   resource until `Present`.
3. **Prototype one stereo backbuffer.** Pack left and right eyes side-by-side in
   one `2 * eye_width` by `eye_height` backbuffer, use a unique Streamline
   viewport handle and resource subrects for each eye, tag both viewports under
   the same frame token, then issue one `Present`. This is the candidate route
   because the public DLSS-G integration supports multiple viewports only when
   they share one backbuffer.
4. **Apply the hard feasibility gate.** The native-present seam is now proven;
   prove that every generated side-by-side
   frame can be obtained with its exact generation index and pacing, split into
   a matched binocular pair and copied to XR-owned/shared eye surfaces. If the
   public or manually hooked Streamline path cannot expose the generated output
   before scanout, or generated presents bypass the proxy, mark direct DLSS-G
   reuse blocked. Do not scrape or recapture the desktop mirror.
5. **Solve pose and display timing.** A generated pair needs an interpolated or
   extrapolated pose for its predicted OpenXR display time. Reusing the source
   pair's pose will add visible head-motion latency; require late pose
   correction/warp after generation or runtime-owned synthesis.
6. **Handle UI and lifecycle.** Use hudless/UI tags so HUD and markers are not
   interpolated as world geometry. Suspend generation for loading, flat panels,
   resize/swapchain recreation and invalid motion-vector history, then restore
   it without the former transparent-duplicate or transition regressions.
7. **Probe the OpenXR fallback in parallel.** Add harness telemetry for
   `XR_EXT_frame_synthesis` and legacy `XR_FB_space_warp`. If VDXR exposes a
   supported extension, provide per-eye depth and motion-vector swapchains,
   correct NDC scaling/offset, reversed-Z near/far and `appSpaceDeltaPose`, then
   chain the synthesis structure to each projection view. This keeps final
   interpolation and predicted-pose handling in the compositor, but is not
   NVIDIA DLSS Frame Generation.

Acceptance requires independently logged rendered-pair, generated-pair,
OpenXR-submission and headset display/stream rates; both generated eyes from
the same source interval; no cross-eye history or rivalry; correct head-motion
latency; stable HUD/markers; clean transitions; and no transparent duplicate.
Only if both the Streamline and runtime-synthesis paths are unavailable should
an independent stereo-aware optical-flow generator be scoped as a larger
follow-up.
